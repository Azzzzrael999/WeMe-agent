# 预约冲突与资源分配规则

## 适用范围

本规则适用于同一会议室、必需参会者、可选参会者或特殊资源发生竞争时的查询、候选生成和最终预约。时间统一使用 Asia/Shanghai、ISO 8601 带偏移时间和 `[start,end)`；会议只能占用连续 30 分钟槽位。Java 业务服务是会议和预约事实源，MySQL 唯一约束是最终裁决，Redis 预占不是最终事实。

## 规则正文

### 房间和参会者冲突

1. 适用对象：所有创建和改期请求。触发条件：候选房间的任一 30 分钟槽位已被确认会议占用。允许行为：系统可以排除该房间，推荐其他满足容量和设备要求的房间或时间。禁止行为：不得覆盖、缩短或移动原会议。处理结果：该候选不可预约；若所有候选都失败，返回无解原因和替代建议。
2. 适用对象：必需参会者。触发条件：任一 REQUIRED 参会者在候选区间存在已确认忙碌槽位。允许行为：系统可以改换时间、缩短会议、调整房间或要求用户编辑参会者。禁止行为：不得把必需参会者冲突降级为 OPTIONAL，不得自动取消或移动其原会议。处理结果：候选被排除，并指出“必需参会者冲突”这一可展示原因。
3. 适用对象：可选参会者。触发条件：OPTIONAL 参会者与候选区间冲突。允许行为：候选可以保留并显示冲突人数、冲突时段和惩罚成本；组织者可以继续选择。禁止行为：不得把可选冲突伪装成全员空闲，也不得泄露无关会议主题。处理结果：候选排序时增加冲突惩罚，并在确认前提示组织者。

### 同时抢订和优先级

多人同时提交同一房间、同一槽位时，系统以数据库唯一约束和先成功提交的事务为最终裁决；HTTP 返回顺序不是裁决依据。失败请求必须收到稳定业务错误码，并可以重新查询新事实。VIP、董事会、公司级或客户会议可以影响候选排序和审批，但不能绕过 MySQL 唯一约束，也不能自动移动已确认会议。优先级只用于尚未确认的候选分配；当两个已确认会议冲突时，系统不替任一方改期。

适用对象是调度系统；触发条件是并发请求或高优先级会议请求；允许行为是保留先完成事务的确认结果、为失败方提供候选；禁止行为是依据用户身份直接覆盖已确认占用；例外仅限管理员在原会议组织者明确取消后释放的槽位；处理结果是成功方保持确认，失败方进入冲突或重新规划。

### 无解与替代建议

无解时必须保留原始硬约束，并按以下顺序建议：第一，改换房间；第二，改换时间；第三，缩短会议但仍保持 30 分钟槽位；第四，将 OPTIONAL 参会者改为不参加，但只有用户明确接受才可执行。系统可以展示最多 3 个候选。不得建议取消、移动或修改他人会议；不得在没有用户同意时放宽 REQUIRED、容量、设备或保密约束。

### 冲突信息展示边界

用户可以看到冲突类型、冲突参会者姓名（仅限其有权查看的人员）、冲突时间区间、房间名称和替代建议。用户不得看到无关会议主题、会议正文、访客资料、薪酬、人事或客户数据。对无权限的冲突，系统只返回“存在权限范围内不可用的资源”，不返回具体内容。Trace 只记录脱敏结构化摘要。

### 候选确认前的资源核对

组织者在选择候选前必须核对房间、时间、实际人数、REQUIRED 参会者、OPTIONAL 冲突、LARGE_SCREEN、WHITEBOARD、VIDEO_CONFERENCE 和审批条件。允许行为是对候选提出 EDIT 或反馈，要求系统重新规划；禁止行为是只看房间名称或“推荐”标签就跳过冲突说明。处理结果是候选缺少任一硬约束时不能进入确认。热门异步预约返回结果后，如果事实已经变化，旧候选必须作废并重新生成，不得复用旧冲突截图。

## 例外与冲突处理

会议类型或房型专项规则的优先级条件可以改变排序，但不能破坏硬约束。专项规则优先于通用规则；安全与保密规则优先于资源便利。同步确认发生 409 或热门异步预约最终冲突时，Scheduling Agent 必须重新读取 Java 的忙闲和房间事实，排除失败候选后重新求解，并再次生成草案；Agent 不得绕过 HITL 直接写入。

## 常见问题

### VIP 会议能否自动移动普通会议？

不能。VIP 只影响未确认候选排序或审批，系统不得自动移动他人会议。

### OPTIONAL 参会者冲突能否预约？

可以保留候选，但必须明确提示冲突并计入排序惩罚；组织者仍需确认。

### 同时抢订谁成功？

由数据库事务和唯一约束裁决，不能根据 HTTP 返回先后或身份猜测。

### 无解时可以建议取消别人会议吗？

不可以。只能建议换房间、换时间、缩短时长或由用户明确编辑参会者。

### 冲突详情可以展示到什么程度？

只展示用户有权限查看的冲突类型、人员和时段，不展示无关会议正文。
