# 全功能演示与智能编排对抗场景

## 1. 目标与使用方式

本文档不是只用于“顺利演示”的话术清单，而是一套面向产品缺陷的验收剧本。它同时回答四个问题：

1. 每个已交付功能如何串成一条可信的企业会议流程。
2. 用户换一种说法、漏说信息、临时改口或混用中英文时，Agent 是否仍能正确理解。
3. 只读查询、制度问答和写入意图是否严格分离，所有写入是否停在 HITL。
4. 失败、冲突、歧义、无解、重放和权限越界时，系统是否给出可继续处理的结果。

自动对抗套件从浏览器相同的 Java 公共入口 `/api/v1/**` 发起请求，不直连 Python。它使用虚构演示账号，所有生成的 HITL 草案都会执行 `REJECT`，并对改期/取消涉及的正式会议做前后快照比对。报告不保存 JWT、确认令牌或原始 SSE 正文。

## 2. 演示角色与产品边界

- 张三：研发中心员工，作为主要演示用户、会议发起人和参会者。
- 李四、王五、赵六、孙琪、周经理：用于个人、多人、小组和负责人场景的虚构员工。
- 管理员：只用于员工、会议室和异常资源管理；普通员工不能获得这些权限。
- Java：会议、员工、会议室、通知、生命周期、异常单和最终写入的事实源。
- Agent：负责理解、制度检索、工具编排、候选解释和 HITL 草案，不可绕过 Java 写正式会议。
- 时间：服务端统一使用 `Asia/Shanghai` 和带 `+08:00` 偏移的时间；这些技术字段不直接作为页面产品文案展示。

明确不在演示范围内：外部日历、邮件、视频平台、SSO、RSVP、附件二进制、会议统计、自动移动他人会议。

## 3. 自动化的 16 组多轮智能编排对抗场景

执行器会根据当前日期和已有演示会议生成未来时间，因此下表用 `D1/D2/D3` 表示运行时选择的未来日期。

### A01 正式、多人员、多硬约束创建

**用户：**“请安排李四和周经理在 D1 14:00 至 17:00 之间开 60 分钟支付网关发布准备会，至少 8 人，需要大屏和白板。先给候选，不要直接确认。”

**应答与断言：**识别为创建会议；解析两名必需参会者、容量和两类设备；查询人员忙闲和会议室；给出 Top 3；只生成 CREATE 草案并等待确认，不能直接创建。

**专门挑错：**“先给候选”不能把创建意图误路由为纯会议室推荐；“大屏和白板”不能漏掉任一硬约束。

### A02 口语、近义词和模糊人数

**用户：**“麻烦 D2 午后帮我跟李四碰一下，半小时就行，四五个人，找个能投屏的屋，先让我挑。”

**应答与断言：**“碰一下”仍是创建会议，“半小时”规范为 30 分钟，“午后”形成候选窗口，“投屏”规范为大屏设备；进入 HITL。

**专门挑错：**不能把口语判为闲聊，不能把“四五个人”错误当作员工姓名或精确参与者列表。

### A03 信息不足后一次补齐

**第一轮用户：**“帮我安排一个上线评审。”

**Agent：**集中询问日期/时间范围、时长、必需参会者等真正阻塞调度的信息；状态为“等待补充”，不得查房或创建草案。

**第二轮用户：**“定在 D3 下午 1 点到 5 点这个范围，开 90 分钟；李四、赵六必须参加，8 个人，要大屏，其他没要求。”

**应答与断言：**复用同一 Run、需求修订号递增、补齐约束后查询事实并进入 HITL。

**专门挑错：**第二轮不能丢失第一轮的“上线评审”主题，也不能另起一个无上下文任务。

### A04 单独“2 点”的上午/下午歧义

**第一轮用户：**“明天 2 点帮我和李四开一小时会。”

**Agent：**询问是凌晨/下午等明确时段，不擅自按 14:00 排会。

**第二轮用户：**“是下午两点，4 个人，不需要额外设备。”

**应答与断言：**在同一 Run 中确定为 14:00，保持一小时和李四，生成候选与草案。

**专门挑错：**澄清回复不能被当成一个新的创建请求；“不需要额外设备”应结束设备追问。

### A05 续聊中同时删人与加人

**第一轮用户：**“帮我和李四、赵六约个会，周经理可选。”

**Agent：**保存必需/可选参会者并追问时间、时长等缺失项。

**第二轮用户：**“调整参会人：赵六不参加了，加上孙琪必须参加；D1 下午 1 点到 5 点内找 60 分钟，6 个人，要白板，其他没有要求。”

**应答与断言：**最终必需名单保留李四、新增孙琪、删除赵六；不能只处理删除而漏掉新增；周经理保持可选语义。

### A06 “我的小组”必须经过组织事实解析

**用户：**“给我的小组约个 D2 下午的 60 分钟周会，至少 12 人，要白板，房间你挑，先给方案。”

**应答与断言：**调用服务端人员范围解析工具，从当前登录用户的有效组织关系得到人员；不能信任模型凭空列名字；进入 HITL。

### A07 中英混合与英文时段

**用户：**“Please book a 30-minute sync with 李四 on YYYY-MM-DD afternoon, 4 people, whiteboard required. Show options first.”

**应答与断言：**识别 CREATE_MEETING；英文日期、afternoon、30-minute、whiteboard 与中文姓名均被保留；生成候选并等待确认。

**专门挑错：**不能因为英文动词 `book` 路由失败，也不能在来源一致性检查中误拒绝英文时段。

### A08 只找共同时间，不预约

**用户：**“帮我看看李四和周经理在 D1 上午 9 点到 12 点有没有一起空出的 60 分钟，只查时间，不预约。”

**应答与断言：**识别 FIND_COMMON_TIME；查询通讯录与忙闲；返回候选后直接完成；不得调用建草案工具、不得出现 HITL。

### A09 只推荐会议室，不预约

**用户：**“D2 13:00 到 17:00，8 个人，给我找带大屏和白板的会议室，只推荐，不要预约。”

**应答与断言：**识别 RECOMMEND_ROOM；只查询符合容量、设备和时段的房间；返回候选后完成，不创建草案。

### A10 VIP 制度有据回答

**用户：**“接待重要客户能直接用 VIP 会议室吗？请只按公司制度回答，并告诉我依据。”

**应答与断言：**只引用 VIP/高管会议室制度的有效 chunk；回答中说明适用条件；不得引用架构评审或普通设备制度凑证据。

### A11 架构评审设备制度有据回答

**用户：**“做架构评审时，会议室设备有什么硬性或建议要求？只说知识库能证明的。”

**应答与断言：**只允许引用架构评审标准和相关设备制度；硬性与建议要求不能混淆；不得把文档标题当作正文证据。

### A12 知识库无答案时诚实拒答

**用户：**“公司是不是规定每月最后一个周五开会必须穿蓝色衣服？没有制度依据就直接说没查到。”

**Agent：**“未找到可验证的会议制度证据。”

**应答与断言：**无引用、无编造、无“通常公司会……”一类泛化补充。旧问题“周五下午绝对不能开会”在正式 22 份制度上线后已有“工作日 09:00–18:00 可直接预约”的反证，不再属于知识库无答案样本。

### A13 明确会议 ID 的改期预览

**用户：**“把会议 ID N 挪到 D 上午 10 点，时长、人员和设备都不变，先给我看变更草案。”

**应答与断言：**识别 MODIFY_MEETING；从 Java 获取目标会议并继承未改变约束；给出 Before/After 和 RESCHEDULE 草案。执行器随后 REJECT，并验证正式会议快照完全不变。

### A14 口语取消预览

**用户：**“把 N 号会议撤掉，不过先让我看清楚会取消哪一场，别直接动。”

**应答与断言：**“撤掉”识别为 CANCEL_MEETING；展示准确目标和取消影响；只生成取消预览。执行器 REJECT 后验证会议仍为原状态。

### A15 同日多场会议的目标消歧

**第一轮用户：**“把 D 下午的会挪到第二天上午，其他照旧。”

**Agent：**若同一时段存在多场可管理会议，列出可验证的候选目标并要求用户明确，不能任选一场。

**第二轮用户：**“是‘架构评审’这场，改到 D2 上午 10 点，其他不变。”

**应答与断言：**继续保持 MODIFY_MEETING，定位指定标题，继承原约束并生成 RESCHEDULE 草案；执行器 REJECT 并核对涉及会议未变化。

### A16 无解后在同一 Run 放宽时间

**第一轮用户：**“我必须参加，想在 D 的已占用时段内开 60 分钟会议，4 个人，无设备要求；如果排不开请说具体原因。”

**Agent：**返回结构化 `plan.unsat`，指出人员或房间的具体冲突，并保持可续聊状态；不得伪造候选。

**第二轮用户：**“那改到 D2 上午 9 点到 12 点这个范围，时长和其他要求不变。”

**应答与断言：**“那改到”是对尚未创建会议需求的修订，意图仍为 CREATE_MEETING，不得错误转成改期；保留 60 分钟、容量和无设备要求，重新查询并进入 HITL。

## 4. 全产品演示流程

以下流程覆盖智能编排之外的真实业务面，适合答辩或交付验收时按顺序演示。

### F01 登录、角色与通讯录

1. 张三登录，工作台只显示员工可用入口。
2. 打开会议创建表单，人员控件展示中文姓名和部门，不展示账号、邮箱、密码或内部字段。
3. 普通员工直接访问员工管理或会议室管理接口，应得到稳定的 403；导航不应出现管理入口。
4. 管理员登录后查看员工列表，完成新建、编辑、重置密码、停用再启用；用旧版本提交编辑应触发乐观锁冲突。

**风险点：**前端隐藏入口不能代替服务端鉴权；停用用户持有的旧 JWT 必须在下一次请求失效。

### F02 手动预约、更新、取消和幂等

1. 在“我的会议”创建一场 90 分钟会议，选择三段连续的 30 分钟槽位、房间和多名参会者。
2. 使用相同幂等键和相同请求重放，必须返回同一会议；相同键但不同参数必须拒绝。
3. 先提交一次会导致冲突的更新，确认会议原状态未部分改变；再提交合法更新。
4. 取消会议，确认槽位释放且组织者/参会者收到中文站内通知。

### F03 并发最终裁决

1. 对同一房间、同一时段发起 100 个不同幂等键请求，最终只能有一个正式会议。
2. 对同一请求用同一个幂等键并发 100 次，所有成功响应应指向一个会议。
3. 验证数据库最终会议数和槽位数，而不是只比较 HTTP 状态码。

**风险点：**Redis 预占不是最终事实，MySQL 唯一约束必须能在竞态下裁决。

### F04 HITL 的接受、编辑与拒绝

1. 用 A01/A02 话术生成 CREATE 草案。
2. 选择 `EDIT`，修改候选或约束；系统必须重新校验并返回新的确认版本，不能立即写正式会议。
3. 对一条草案执行 `REJECT`，确认正式会议不存在。
4. 对另一条合法草案执行 `ACCEPT`，确认只写入一场会议；重复确认令牌不能重复写。

### F05 HOT 异步预约与结果恢复

1. 构造热门房间/时段草案并接受，Java 先返回 `PENDING + requestNo`，事务中不得提前存在正式会议。
2. Outbox 经 RocketMQ 至少一次投递，消费者以事件和业务终态幂等完成预约。
3. 前端刷新或 Agent checkpoint 恢复后仍能查到 SUCCESS/CONFLICT 终态。
4. 重放同一消息不能创建第二场会议。

**演示前提：**本地 `.env` 默认关闭 Agent 业务结果回调；演示 HOT 回调恢复时需显式设置 `AGENT_CALLBACK_ENABLED=true` 后重建相关服务。日常本地环境保持关闭。

### F06 失败 Run 的需求基线恢复

1. 让一个已收敛需求的 Run 进入可恢复失败状态。
2. 在恢复页查看最后有效 Requirement，创建新 Run 时带 `baseRunId`。
3. 输入“参会人去掉赵六，继续查询”，确认新 Run 保留日期、时长、设备和软偏好，只删除赵六。
4. 越权引用他人的 Run 或不可恢复状态应返回稳定冲突码。

### F07 会议室资源与可用性

1. “会议室”页展示 20 间启用资源、中文房型和中文设备；切换日期与筛选会重新查询真实槽位。
2. 服务端尚未返回的槽位显示“待查询”，不得伪装成“全天不可用”。
3. 同一天多个请求乱序返回时，旧请求不能覆盖当前选中日期。
4. 从房间页发起快速创建，仍需选择人员并走 Java 的正式校验。

### F08 消息中心与接收人隔离

1. 完成创建、变更、取消，分别查看组织者与参会者的中文通知。
2. HOT PENDING、冲突和幂等重放不得制造成功通知。
3. 单条已读和全部已读应幂等，侧栏未读数同步刷新。
4. 普通员工不能读取他人通知，管理员也没有跨用户读取特权。

### F09 会议室失效与异常重排

1. 管理员将一间承载未来会议的房间切为不可用；系统在同一事务创建唯一异常单，只通知发起人，不自动移动会议。
2. 发起人进入“异常重排”，查看继承约束、原房间失效原因和 Top 3 同时段替代房间。
3. 用过期的会议版本或异常单版本提交，必须冲突并刷新；用最新双版本确认后才完成换房。
4. 也可跳转智能编排，页面只预填目标会议与约束，不自动发送；最终仍走 RESCHEDULE HITL。
5. 原房间恢复时，尚未处理且仍使用该房间的异常单转为 RESTORED 并通知发起人。

### F10 会前议程、材料和动态清单

1. 打开未来已确认会议，添加多个议题、负责人、预计时长和顺序。
2. 添加材料元数据，先标记缺失，再补齐；材料仅记录链接/版本/权限元数据，不上传二进制。
3. 动态准备清单应聚合人员、房间、设备、议程、材料；由缺失变为 READY。
4. 参会者可查看但不可修改组织者的准备内容；使用旧 `expectedVersion` 保存必须冲突。
5. 重复运行 24 小时、30 分钟和缺失项扫描，不得重复通知。

### F11 自动完成与会后结构化草案

1. 会议结束时间到达后，调度器将 CONFIRMED 幂等转为 COMPLETED。
2. 发起人提交不超过 20000 字的文本会议记录。
3. Agent 只生成“纪要、决策、行动项草案”；未知负责人确定性归一为空，不调度会议、不直接写正式会后记录。
4. Provider 不可用或输出越界时，草案状态为 FAILED 且可重试，错误码稳定。

### F12 会后 EDIT/REJECT/ACCEPT 与行动项催办

1. 发起人先执行 `EDIT`，修改纪要、决策或行动项；正式表仍为空，随后必须再次确认。
2. `REJECT` 后不生成正式记录；`ACCEPT` 在单事务写入纪要、决策和行动项。
3. 非发起人不能审核；负责人只能更新自己的行动项；旧版本更新必须冲突。
4. 临期和逾期扫描分别生成通知，重复扫描按截止时间事实快照去重。

## 5. 本轮发现并修复的问题

| 缺陷 | 用户表现 | 修复与回归 |
|---|---|---|
| 制度证据只传标题、无证据仍生成引用 | 回答看似专业但依据不相关 | Policy 接收完整检索正文；空证据返回固定诚实回答；A10–A12 与引用门禁覆盖 |
| 口语创建被路由为推荐房间 | “先让我挑”后只推荐房间，无法完成预约流程 | 增加正式/口语/英文创建路由别名并固定写入意图；A01、A02、A07 覆盖 |
| 续聊同时删人与加人时只处理一侧 | 用户删赵六、加孙琪后名单错误 | 确定性合并 REMOVE+ADD；A05 覆盖 |
| “那改到……”将未创建需求误判为改期 | 无解放宽时间后开始找目标会议 | 仅显式跨意图目标才改变意图；续聊继承 CREATE；A16 覆盖 |
| 模型只完成部分只读 Tool 后要求“继续查询” | 明明信息齐全却多一轮无意义追问 | 在同一 Tool Gate/Trace 中确定性补齐缺失的忙闲/房间只读事实；A08、A09 和单测覆盖 |
| Agent loop 代码上限扩大但 Schema 仍为 4 | 复杂场景偶发 `AGENT_GRAPH_FAILED` | 代码、Pydantic Schema 和测试统一为最多 6 轮 |
| 英文/ISO 日期在来源一致性校验中被误拒绝 | 中英混合请求无法生成候选 | 支持英文时段、ISO 日期和大小写不敏感来源核验；A07 覆盖 |
| Java SSE 约 30 秒超时并转成错误 JSON | 慢模型请求在前端中断 | 公共 SSE 异步超时可配置为 300000ms，并在 Compose/部署文档记录 |
| HOT Smoke 写死旧房间 ID | 扩充会议室后正确候选也被判失败 | Smoke 改为按设备、园区和最终不同房间语义断言 |
| Fixture 未解析偏好园区 | 热门场景无法稳定选中目标资源 | Fixture 从用户消息解析园区偏好，恢复确定性 HOT 回归 |

## 8. 剩余风险与下一轮建议

1. 16 条代表性对抗场景已经覆盖主要表达变化，但不等于自然语言空间穷尽；每次改 Prompt、模型或工具 Schema 后应重跑完整 16+40 门禁。
2. 约束字段 F1 为 95.31%，虽高于当前门禁但仍非 100%；后续应把新增真实失败样本追加到评测集，而不是只优化已有话术。
3. Live model 延迟当前 P95 约 26 秒；Java SSE 已放宽到 300 秒，但产品上仍应持续观察慢请求和 Provider 限流。
4. 本地默认关闭 HOT 的 Agent 回调。做完整异步演示前需按 F05 明确开启，演示后恢复默认，避免把环境开关误判为产品缺陷。
5. 演示数据会保留必要的审计历史；自动测试不删除数据库卷。用于公开录屏前，应重新筛选消息与会议列表，避免把历史 Smoke 记录误当成当前业务数据。
